# WebDAV 반복 검증 비용 개선 검토

후속 구현: [v1.0.19 확정 정책·설정·복구](V1_0_19_WEBDAV_VERIFICATION.md).
아래는 초기 검토 기록이며, 확정 회수는 **14회**이고 신규 대용량 단일 검증도 구현 범위에 포함한다.

검토일: 2026-09-06. 기준: v1.0.18 코드 `b2d0211`과 사용자가 제공한 운영 수치.
이 문서는 설계 검토안이며 런타임 코드·설정·운영 저장소에는 변경을 적용하지 않았다.
원본 운영 `performance.json`과 요청별 로그는 이 작업 공간에서 확인되지 않았다.

## 권고

**기존 객체의 전체 재검증을 주기화하는 것이 우선이다.** 신규 업로드 검증과 기존
객체의 보존 상태 감사를 분리하고, 검증 성공 이력을 실행 간 보관한다. 초기에는 신규
업로드의 임시·최종 경로 검증을 유지한다. 대용량 generation 파일의 검증을 1회로 줄이는
변경은 실패 후 복구 처리까지 갖춘 다음 단계로 진행한다.

변경이 없을 때 Export·업로드를 생략하는 `no_change`는 이미 구현되어 있다. 따라서
전체 업데이트를 몇 회씩 미루는 것보다, `no_change` 전에 수행하는 원격 전체 읽기를
줄이는 것이 데이터 갱신 지연 없이 적용할 수 있는 개선이다.
임베딩 cache hit 100%만으로 corpus/contract 불변을 판단할 수는 없다. OCR 실패 재처리와
미완료 OCR 캐시 복구 조건도 기존처럼 확인해야 한다.

## 2. 실제 반복 읽기 경로

| 경로 | 현재 동작 | 개선 지점 |
|---|---|---|
| 현재 배포본 확인 | DB + vectors + 고유 PDF/OCR 전체 GET·SHA-256, CAS는 순차 실행 | 실행 간 검증 이력·감사 주기 도입 |
| 기존 CAS 재사용 | 목적지 HEAD 후 전체 GET | 같은 실행에서 이미 검증한 객체 재사용, 이후 이력 기반 재사용 |
| 새 객체 게시 | PUT(temp) → GET(temp) → MOVE → GET(destination) | 대용량 generation부터 단일 검증을 후속 검토 |
| `no_change` | 전체 원격 검증 이후 corpus/contract 비교 | 제어 파일 확인과 전체 본문 감사를 분리 |

현재 배포본 검증은 [Worker WebDAV](../apps/cardrag-worker/src/cardrag_worker/webdav.py)
`validated_current_generation()`(309–368행)에 있다. 포인터가 같으면 동일 client instance
안에서는 결과를 재사용하지만, 캐시는 메모리뿐이어서 새 Worker 실행에는 남지 않는다.
[Pipeline](../apps/cardrag-worker/src/cardrag_worker/pipeline.py)은 2,963행에서 이를 먼저
호출하고, 3,076행 부근에서 `no_change`를 반환한다.

[Core CAS](../packages/cardrag-core/src/cardrag_core/cas.py) `_publish()`는 기존 목적지를
69–70행에서 HEAD+GET으로 확인하고, 새 업로드를 88행·101행에서 두 번 검증한다.
따라서 현재 배포본 검증에서 읽은 CAS를 게시 과정에서 다시 읽을 수 있다.
게시 CAS 작업은 Pipeline 5,811–5,834행에서 이미 동시성 16을 사용한다.
단순히 업로드 병렬 수를 늘리는 것은 첫 번째 해결책이 아니다.
이 작업 배정은 `validated.objects`를 그대로 순회하므로, 여러 문서가 같은 CAS 경로를
참조하면 같은 실행에서도 중복 요청이 생길 수 있다. 로컬 seal의 참조 수·정합성 검증은
유지하면서 원격 작업만 경로·해시·크기별로 합치고 진행 중인 검증 결과도 공유할 수 있다.

이전 배포본의 DB/vector도 새 번들과 크기가 같다고 가정하면 대용량 파일 읽기는
`기존 7.89GB + 신규 임시 7.89GB + 신규 최종 7.89GB = 23.67GB`가 될 수 있다.
나머지 6.02GB를 CAS·기타 읽기로 설명할 가능성이 있으나, 이는 구조에 따른 예시이지
원본 로그에서 확인한 분류가 아니다.

## 3. 검증 주기 설계안

다음 값은 운영 실험을 위한 **제안 초기값**이며 현재 지원하는 환경변수가 아니다.

| 대상 | 일반 실행 | 전체 검증 조건 |
|---|---|---|
| pointer / READY / manifest | 매번 읽고 해시·상호 참조·세대·계약 확인 | 항상 유지 |
| 신규 CAS와 검증 이력 없는 기존 객체 | 업로드 또는 재사용 시 전체 SHA-256 검증 | 항상 유지 |
| 검증 이력이 있는 기존 DB/vector/CAS | 이력 대조와 존재·크기 확인, 제공되면 ETag 변화 확인 | 7회 실행 또는 7일 또는 신규 CAS 누적 10GiB 중 먼저 도달 |
| 무결성 오류·원격 복원·이력 소실 | 빠른 재사용 중단 | 영향 범위 즉시 검증, 범위를 모르면 전체 검증 |

스케줄 예시는 [Worker timer](../deploy/worker/cardrag-worker.timer)의 매일 03:00 실행을
기준으로 한다. 실제 운영 주기는 별도로 확인해야 한다. 전체 검증 직후 첫 6회는 가볍게
확인하고 7번째 도래 실행에서 전체 검증한다. `no_change`도 회수에 포함하며 실패·재시도로
기한이 밀리지 않게 한다. 7일은 마지막 **성공한 전체 검증**부터 계산한다. 배치가 며칠
중단되면 다음 실행에서 즉시 검증하고, 실행 중단 중에도 7일 내 탐지가 필요하면 별도의
감사 timer가 필요하다.

누적 용량은 NAS 전체 사용량이 아니라 마지막 전체 검증 이후 성공적으로 새로 저장된
**고유 CAS 객체의 실제 바이트 합계**로 센다. 재시도·중복 참조를 이중 계산하지 않는다.
매번 생성되는 DB/vector 7.89GB는 이 CAS 기준에 넣지 않는다. 임계치에 도달하는 실행은
신규 업로드 검증 후 포인터 전환 전에 만기 감사를 완료한다. 기존 증거로 이미 그 실행에서
검증한 바이트는 다시 읽지 않는다. 10GiB는 변경량에 맞춰 조정할 값이다.

여기서 전체 감사 대상은 snapshot으로 고정한 현재 활성 세대의 DB/vector와 참조 CAS이며,
새 게시가 있으면 후보 세대의 검증 증거까지 결합한다. 모든 과거 세대와 원격 미참조 파일을
매번 전수 스캔하는 의미가 아니다. 감사·게시 전후 포인터 변경을 확인하고, 보존한 과거
세대의 복구 가능성 검사는 별도 보존 정책에 맞춰 수행한다.

총 저장소 사용률 80% 같은 기준은 용량 점검·보존 정책·GC 판단에 적합하다. 변경량이
0이어도 저장된 파일에 손상이 생길 수 있으므로 용량만으로 검증 시점을 정하면 안 된다.
감사와 GC는 별도 작업으로 유지하고, 검증 주기 변경이 삭제 정책을 변경하지 않게 한다.

### 실행 간 검증 이력

Worker state에 다음 정보를 원자적으로 저장한다.

- 객체 이력: 원격 endpoint/namespace 식별자, 상대 경로, 기대 SHA-256·크기,
  검증 성공 시각·run ID·검증 방식·policy version, 관측된 ETag와 크기.
- 세대 이력: channel, generation ID, pointer/READY/manifest 해시, 해당 세대의 객체
  집합 검증 완료 여부. CAS 이력은 경로·해시로 세대 간 재사용할 수 있다.
- 감사 이력: 마지막 성공 시각, 다음 만기 실행 회수, 누적 고유 CAS 바이트,
  진행 중인 감사의 대상 snapshot과 진행 상태.

현재 [Worker state](../apps/cardrag-worker/src/cardrag_worker/state.py)의 `publish`
테이블(325–337행)은 게시 이력이지 객체별 원격 검증 증거가 아니다. `published_at`만으로
검증 성공을 추정하거나 기존 모든 레코드를 검증 완료로 일괄 승격해서는 안 된다. 도입 시
첫 전체 검증으로 기준을 만들고, 이후 신규 게시 검증이 성공할 때 이력을 남긴다.

검증을 생략하거나 HEAD에 성공한 것만으로 `verified_at`을 갱신하지 않는다. 전체 검증이
부분 실패하면 전체 성공 시각·회수를 초기화하지 않는다. 상태 파일 손실, 서버/namespace
변경, 복원, 관련 GC 삭제, 크기/ETag 불일치는 이력을 무효화한다. 포인터만 바뀐 경우
새 제어 파일을 검증하고 새 세대의 증거를 확인하되 공유 CAS의 유효한 증거는 재사용한다.

이 정책은 **보존 중 발생한 손상을 탐지하는 시점을 늦추는 선택**이다. HEAD의 크기와
ETag가 같아도 서버가 감지하지 못하는 디스크 손상을 직접 증명하지 못한다. 강한 ETag를
제공하지 않는 서버에서도 이력+주기 감사를 선택할 수 있지만, 이를 본문 전체 검증과 같은
수준의 증거로 기록해서는 안 된다. 이 탐지 지연을 허용하지 않는 환경에는 매번 전체 GET을
수행하는 strict 모드를 유지한다.

원격 불일치가 발견되거나 만기 감사를 완료하지 못하면 새 포인터 게시와 성공 판정을
막고 기존 MCP 서비스 상태를 유지한다. 통신 오류를 객체 소실로 취급하거나 손상된 불변
객체를 자동 덮어쓰는 방식으로 처리하지 않는다.

## 4. 간소화 방안별 우선순위

| 순서 | 변경 | 효과와 조건 |
|---|---|---|
| 1 | 같은 실행에서 검증한 CAS를 재사용 | 현재 세대 확인 후 재게시 과정의 중복 GET 감소. 내부 쓰기/삭제와 관측된 변경 시 무효화 |
| 2 | 실행 간 이력 + 7회/7일/10GiB 감사 | 이전 DB/vector와 기존 CAS의 반복 읽기 감소. 신규 업로드는 기존 이중 검증 유지 |
| 3 | 기존 객체 HEAD를 필요한 CAS prefix별 PROPFIND로 묶기 | 본문 절감 후 남는 HTTP 왕복 감소. 실제 참조가 있는 prefix만 조회 |
| 4 | 새 generation DB/vector를 최종 GET 1회로 검증 | 해당 신규 파일의 read-back 바이트 50% 절감. 실패 경로 복구가 선행 조건 |
| 5 | 서버 측 실제 바이트 해시 계산 | WAN 다운로드를 줄이는 별도 설계. NAS 내부 I/O와 서버 기능 확인 필요 |

3단계에서는 Depth:1에 필요한 속성만 요청하고, 각 응답의 경로·상태·크기를 확인해야 한다.
누락·불완전 응답을 성공으로 처리하지 않으며 HEAD/GET으로 보완한다. 전체 namespace의
Depth:infinity 검색은 필요하지 않다. 순차인 현재 세대 CAS 감사의 제한된 병렬화도 검토할
수 있으나, 기존 게시 병렬 16과 별개로 2–4부터 실제 대역폭·NAS 응답을 측정한다.

### 신규 업로드의 단일 검증

후속 후보는 `로컬 해시 → PUT(temp) → MOVE(Overwrite:F) → GET(final) → READY/포인터`
순서다. 최종 SHA-256가 맞기 전에는 세대를 활성화하지 않는다. 마지막 GET을 없애고
임시 GET만 남기는 방식은 최종 경로의 바이트를 직접 확인하지 못하므로 우선 추천하지 않는다.

임시 GET을 제거하면 PUT 중 손상된 바이트가 불변 목적지를 먼저 차지할 수 있다. 현재
코드는 다음 재시도에서도 그 경로의 불일치를 발견하고 중단하며 자동 복구하지 않는다.
미활성 generation의 새 ID 발급/격리·재시도, 중단 지점 복구를 설계한 뒤 대용량
DB/vector부터 적용한다. 여러 세대가 공유하는 CAS에는 초기 이중 검증을 유지한다.
MOVE 409/412 충돌은 목적지가 다른 writer의 객체일 수 있으므로 최종 전체 검증이 필수다.
업로드 전 로컬 SHA-256와 파일 식별자 확인, `pre_commit` 검사는 유지한다.

### ETag·manifest·archive의 한계

ETag는 SHA-256라는 보장이 없는 불투명한 버전 식별자다. 같은 URL의 변화 감지에 활용할
수 있으나 로컬 SHA-256와 문자열을 직접 비교하면 안 된다. MOVE로 경로가 바뀌면 ETag가
달라질 수도 있다. [RFC 9110 §8.8.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.3),
[RFC 4918 §8.8](https://www.rfc-editor.org/rfc/rfc4918.html#section-8.8).

서버의 SHA-256 digest 기능은 실제 Synology 버전·설정·응답을 확인한 뒤 평가한다.
`Repr-Digest`와 `Content-Digest`의 대상이 다르며, 단순히 요청에 해시를 보내거나 서버가
이를 보관·반환한다고 저장된 전체 파일을 다시 해시했다는 증거는 되지 않는다. digest 요청
헤더의 지원도 필수가 아니다. [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html).
서버에서 실제 파일을 읽어 계산하는 작업과 정확한 경로·버전·크기 바인딩이 확인되어야 한다.

manifest에는 이미 기대 해시가 있다. manifest만 다시 읽거나 자체 해시를 검증하는 것은
그 파일이 참조하는 실제 객체가 온전하다는 증거가 아니다. 일괄 서버 해시 결과는 별개다.
tar/pack은 작은 파일 요청을 줄일 수 있지만 본문 읽기량 자체가 없어지지는 않는다.
현재 CAS 경로, OCR 캐시, MCP 개별 문서 읽기, GC·복구 방식을 함께 바꿔야 하므로 단기
개선보다 후순위다. 기존 CAS를 그대로 두고 tar도 추가하면 전송·저장량이 늘 수 있다.

## 5. 업데이트 자체를 모아서 수행하는 선택지

`no_change`가 이미 있으므로 동일 입력·계약에서는 별도의 N회 게시 설정이 필요하지 않다.
입력이 조금씩 변하는 경우에는 다음 조건으로 Export·게시를 묶는 별도 기능을 만들 수 있다.

```text
변경 있음 AND (
  마지막 게시 후 N회 수집
  OR 변경 문서 수/고유 변경 바이트 임계치
  OR 최대 허용 갱신 지연 도달
  OR 강제 게시 또는 즉시 반영 대상 변경
)
```

비교 기준은 직전 실행이 아닌 마지막 성공 게시본이다. 미게시 변경은 state에 보관하고
재시작·실패로 사라지지 않게 한다. 수집, Export, 게시 완료 상태를 구별하고 대기 상태를
`no_change`로 기록하지 않는다. 변경 건수/바이트는 매번 생성되는 번들 전체 크기가 아니다.

매일 실행한다면 3회마다 게시하는 것은 반영이 약 3일 간격이 될 수 있다. 카드 약관·혜택의
갱신 지연을 발생시키므로 기본 권고는 **변경된 데이터는 계속 게시하고 검증만 주기화**하는
것이다. 게시 묶음 기능은 허용 가능한 지연이 정해진 후 선택한다.

## 6. 예상 절감과 검증 계획

아래는 제공된 GB 단위를 그대로 사용한 조건부 바이트 모델이다. 이전 배포본의 검증
이력이 있고, 감사 만기가 아니며, 이번 신규 업로드가 사실상 DB/vector인 실행을 가정한다.
원본 로그에서 원인별 분류가 확인되기 전에는 실측 성과로 사용하지 않는다.

| 단계 | 예상 검증 GET 본문 | 29.69GB 대비 |
|---|---|---|
| 현재 보고값 | 29.69GB | 기준 |
| 반복 감사 생략, 신규 이중 검증 유지 | 약 15.78GB + 신규 CAS 검증·기타 | 최대 약 47% 감소 여지 |
| 추가로 신규 DB/vector 최종 검증만 수행 | 약 7.89GB + 신규 CAS 검증·기타 | 최대 약 73% 감소 여지 |

7회마다 기존 객체를 전체 감사하면 그 **반복 감사 부분**의 회당 평균 읽기량은 약
1/7로 줄지만, 전체 파이프라인이나 신규 업로드 비용까지 86% 줄어드는 것은 아니다.
기간·용량 만기로 더 일찍 감사하면 평균 절감률은 낮아진다. 감사일의 긴 실행은 여전히
발생하며 필요하면 대상 snapshot을 고정해 여러 실행에 나누는 순환 감사로 확장한다.
순환 감사에서도 전 객체 최대 검증 나이와 미완료 backlog를 관리해야 한다.

7.89GB를 실제 단일 스트림 7–8MB/s로 받는다면 본문 전송만 약 16–19분이다. 현재
4,125초는 누적 계측이므로 이 계산을 전체 118분에서 그대로 빼서 완료 시간을 예측하지
않는다. v1.0.18 운영 문서의 75분 인수 목표 달성 여부는 변경 후 실제 실행으로 측정해야 한다.

구현 시 최소 확인 항목은 다음과 같다.

1. 현재 세대 확인, 기존 CAS 재사용, 임시 검증, 최종 검증을 별도 reason으로 계측하고
   요청/고유 객체/본문 바이트와 단계별 실제 시작·종료 시각을 기록한다.
2. 이력 없음, 일반 재실행, `no_change`, 7회/7일/바이트 만기, 실패·재시작의 회수·시각
   보존, 부분 감사 실패, 서버/namespace 전환을 검증한다.
3. 누락·크기 변동·같은 크기 바이트 변조·ETag 부재/약함/변동을 확인한다. 주기 정책에서는
   즉시 탐지할 오류와 다음 전체 감사에서 탐지할 오류를 구별해 검증한다.
4. 신규 파일 손상·로컬 경로 교체·MOVE 충돌·MOVE 직후 중단·READY/포인터 게시 순서를
   확인한다. final-only 후보는 손상된 미활성 목적지에서의 재시도까지 검증한다.
5. 기존 strict 모드와 신규 정책을 같은 코퍼스/캐시/네트워크에서 비교한다. 전체 빌드,
   일반 `no_change`, 감사 만기 실행을 따로 측정하고 MCP의 다운로드 검증도 유지한다.

이번 검토에서는 기존 동작 확인을 위해 아래 관련 테스트를 실행했고 **46개 통과**했다.
성능 개선 구현, NAS digest/ETag 기능 확인, 실운영 시간 측정은 수행하지 않았다.

```bash
.venv/bin/python -m pytest -q \
  packages/cardrag-core/tests/test_webdav_cas_facade.py \
  apps/cardrag-worker/tests/test_webdav.py \
  apps/cardrag-worker/tests/test_worker_performance.py
```

현행 [v1.0.18 운영 기준](V1_0_18_WORKER_EFFICIENCY.md)은 `no_change` 전체 원격 검증과
신규 파일 임시·최종 검증을 명시한다. 검증 주기화는 업로드 청크 크기 같은 기존 설정으로
켜는 기능이 아니라, Worker state·검증 API·설정·회귀 테스트·운영 문서를 함께 수정하는
후속 구현 작업이다.
