# 구성요소 개발 가이드

## 1. 문서 목적

이 문서는 신규 CardRAG MCP 시스템을 구현할 때 각 구성요소가 책임져야 할 범위와 구성요소 사이의 인계 조건을 정의한다. 구체적인 API 스키마, 클래스 설계, 데이터베이스 DDL 및 구현 코드는 다루지 않는다.

기준은 다음과 같다.

- 카드사 공시 PDF와 이를 충실하게 전사한 OCR을 사실의 원천으로 취급한다.
- 수집·OCR·구조 분석·임베딩은 오프라인 처리 영역에서 수행한다.
- MCP 서비스는 검증을 통과해 게시된 검색 세대만 읽는 온라인 영역이다.
- 장시간 작업의 성공 여부는 디렉터리 존재가 아니라 명시적인 상태와 검증 기록으로 판단한다.
- 동일 입력과 동일 처리 정책으로 다시 실행해도 중복 부작용이 없어야 한다.
- 레거시의 자산과 계약은 선별적으로 참고하되, 운영 중 DB를 직접 재구축하는 방식과 전체 벡터 순회 방식은 그대로 이식하지 않는다.

## 2. 공통 데이터 원칙

### 2.1 사실 계층과 파생 계층

데이터의 신뢰 순서는 다음과 같다.

1. 원본 PDF와 수집 당시의 출처·해시
2. 페이지 대응 관계를 보존한 OCR 원문
3. 원문 위치를 가리키는 결정론적 레이아웃·섹션 후보
4. 규칙 또는 LLM이 부여한 분류·관계·정규화 값
5. 검색용 chunk, 임베딩 및 색인
6. MCP가 조합해 반환하는 검색 결과

상위 계층은 하위 계층을 대체하지 않는다. 특히 구조 분석이나 LLM이 생성한 문장은 OCR 원문을 덮어쓰거나 원문 인용문으로 사용해서는 안 된다. 모든 파생 정보는 원본 문서 버전, 페이지 또는 원문 범위, 생성 정책 버전까지 역추적할 수 있어야 한다.

### 2.2 식별과 버전

- 상품코드는 반드시 카드사 식별자와 함께 사용한다. 상품코드만으로 문서나 검색 결과를 중복 제거하지 않는다.
- 수집된 PDF의 각 변경본은 별도 문서 버전으로 보존한다.
- PDF 내용 해시, OCR 내용 해시, 구조 스키마 버전, 임베딩 모델·차원, 색인 세대를 기록한다.
- `최신`은 고정된 사실이 아니라 특정 수집 스냅샷을 기준으로 한 판정이다. MCP 응답에는 그 스냅샷 또는 색인 세대를 식별할 정보가 필요하다.
- 같은 내용의 PDF가 여러 경로에서 발견되어도 출처 이력은 유지한다. 물리 저장 중복 제거 여부는 논리 문서 이력과 분리한다.

### 2.3 공통 작업 상태

각 단계는 최소한 다음 의미를 구분해야 한다. 실제 상태명과 저장 형식은 구현 시 결정하되 의미를 축소해서는 안 된다.

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| 대기 | 입력과 선행조건이 준비됨 | worker가 원자적으로 작업을 점유 |
| 실행 중 | 작업 주체, 시작 시각, heartbeat 또는 lease가 존재함 | 완료, 재시도 가능 실패 또는 검토 대기로 전이 |
| 부분 완료 | 일부 페이지나 하위 단위만 성공함 | 성공 단위를 보존하고 미완료 단위를 이어서 처리 |
| 재시도 가능 실패 | 일시적 네트워크·제공자·자원 오류 | 제한된 backoff 후 재시도 |
| 검토 대기 | 자동 판정으로 안전하게 완료할 수 없음 | 사람이 원인과 원문을 확인 |
| 종결 실패 | 입력 자체의 문제 또는 승인된 재시도 예산 소진 | 명시적으로 해제하기 전 자동 반복 금지 |
| 검증 완료 | 산출물 생성과 품질 검증을 모두 통과함 | 다음 단계의 입력으로 사용 가능 |
| 게시 완료 | 검증된 색인 세대가 온라인 서비스에 원자적으로 노출됨 | 읽기 전용 서비스가 사용 |

`실행 중` 상태만 기록하고 방치해서는 안 된다. worker 비정상 종료 후 작업을 회수할 수 있도록 작업 주체, attempt, lease 또는 동등한 복구 정보를 가져야 한다. 작업 점유는 조회 후 별도 갱신하는 방식이 아니라 중복 점유를 막을 수 있는 원자적 절차여야 한다.

### 2.4 공통 실패 분류와 재처리

- 네트워크 timeout, 일시적인 외부 서비스 제한, 호스트 자원 부족은 재시도 가능 실패로 분류한다.
- HTML 오인식, PDF가 아닌 응답, 암호화·손상 PDF, 페이지 누락, 스키마 위반은 원인별로 구분한다.
- 재시도 예산과 backoff는 구성요소 및 오류 분류별로 설정한다. 구체 횟수와 시간은 `결정 필요`다.
- 입력 내용 해시와 처리 정책 버전이 같으면 검증 완료 산출물을 재사용한다.
- 처리 정책, 구조 스키마 또는 임베딩 모델이 바뀌면 영향받는 파생 단계부터 다시 처리한다. 원본 PDF를 다시 수집하거나 OCR을 불필요하게 반복하지 않는다.
- 실패 산출물과 진단 로그는 성공 산출물과 구분하고, 디렉터리 존재만으로 성공 처리하지 않는다.

## 3. PDF 다운로드 및 취합기

### 3.1 역할과 경계

PDF 수집기는 각 카드사의 상품공시실에서 상품과 상품안내장 이력을 발견하고, 검증된 원본 PDF와 수집 provenance를 만드는 구성요소다.

카드사마다 목록·상세 페이지, 다운로드 절차, 이력 노출 방식이 다르므로 카드사별 adapter를 둔다. 공통 orchestration은 식별, 버전 판정, 저장, 재시도, 상태 기록과 검증을 담당하고, adapter는 해당 카드사 사이트 해석과 다운로드에만 책임을 제한한다.

우리카드와 KB국민카드를 우선 지원한다. 신한카드는 개인 신용·체크카드 상품안내장의 현재본과 과거 이력을 신규 adapter로 수집해 BULK 처리의 수집·재개·처리량 시험에 포함한다. 법인·선불카드는 신한 1차 범위에서 제외한다. 신한카드는 레거시 adapter나 corpus가 존재하지 않으므로 신규 구현과 별도 fixture·live 검증이 필요하다.

수집기는 OCR, 구조 분석, 임베딩을 직접 실행하지 않는다. 외부에서 임의로 전달된 URL을 범용 다운로드하는 기능도 온라인 MCP에 노출하지 않는다.

### 3.2 입력

- 카드사별 허용 도메인과 공시실 탐색 설정
- 카드사 식별자와 카드사별 상품 분류 범위
- 이전 수집 manifest와 문서 버전 이력
- 최초 수집인지 일일 증분 수집인지 나타내는 실행 정책
- timeout, 응답 크기 제한, 요청 속도와 재시도 정책
- 최초 수집 시 상품별 최신 PDF 우선이라는 범위 정책

상품코드는 카드사 원천에서 확인한 값을 우선 사용한다. 원천이 안정적인 코드를 제공하지 않는 경우 대체 식별 규칙과 충돌 해소 방법은 카드사별로 `결정 필요`이며, 추정값을 확정 상품코드처럼 저장해서는 안 된다.

### 3.3 출력

- 수정하지 않은 원본 PDF 파일
- 카드사, 상품코드, 상품명, 문서 종류, 출처 URL, 발견·수집 시각을 포함한 문서 버전 기록
- PDF SHA-256, 파일 크기, MIME 및 기본 PDF 유효성 검사 결과
- 동일 내용, 신규 내용, 변경 내용, 사라진 링크를 구분한 discovery 차이 보고서
- 성공·실패·재시도 상태와 오류 분류
- 다음 OCR 단계가 소비할 검증 완료 목록

파일명과 디렉터리명은 표시용 상품명에 의존하지 않고 안전한 canonical 경로 생성 규칙을 거쳐야 한다. 절대경로, 상위 경로 이동, symlink를 통한 저장소 밖 이탈을 막아야 한다.

### 3.4 수집 및 변경 판단

최초 대량 수집에서는 각 상품의 최신 안내장을 먼저 처리하되 과거 버전도 모두 보존 대상으로 수집한다. 기본 검색은 최신본만 대상으로 하고 version 또는 as-of가 명시된 요청에서만 과거본을 포함한다. 법적 이용 조건은 별도 gate로 확인한다.

일일 증분 수집은 다음을 구분한다.

- 처음 발견한 상품 또는 문서
- 같은 상품의 새 기준일·버전
- 동일한 이름이나 URL이지만 PDF 내용 해시가 변경된 문서
- 원천에서는 사라졌으나 기존 스냅샷에 존재하는 문서
- URL 또는 파일명만 다르고 내용 해시가 같은 문서

파일명과 파일 크기만으로 변경 없음을 확정하지 않는다. 원천 목록이 내용 해시를 제공하지 않으면 안전한 임시 영역에 내려받아 PDF를 검증하고 해시를 비교한다. 사라진 문서는 자동 삭제하지 않고 마지막 관찰 시각과 상태를 남긴다.

### 3.5 상태, 실패와 재처리

- discovery와 파일 다운로드의 상태를 분리한다. 목록 탐색 성공이 PDF 수집 성공을 뜻하지 않는다.
- 허용 도메인과 redirect 최종 목적지를 검증하고, 응답을 제한 없이 메모리에 읽지 않는다.
- HTTP 오류, timeout, rate limit은 재시도 가능 실패로 분류한다.
- PDF magic만이 아니라 기본 구조와 페이지 열기 가능 여부까지 확인한다.
- HTML 오류 페이지, 빈 파일, 손상·암호화 PDF는 검토 또는 종결 실패로 분리한다.
- 재처리 시 이미 검증된 동일 해시 파일은 다시 쓰지 않고 이력만 갱신한다.
- 카드사 markup 변경으로 discovery 수가 급격히 변하면 자동 성공으로 게시하지 않고 검토 대기로 둔다.

### 3.6 검증 가능한 완료조건

- [ ] 목표 카드사의 모든 설정된 상품 분류에 대해 discovery 실행 결과가 남아 있다.
- [ ] 수집 성공으로 기록된 모든 항목의 원본 파일이 존재하고 기록된 SHA-256과 일치한다.
- [ ] 모든 원본 파일이 PDF 유효성 및 페이지 열기 검사를 통과했다.
- [ ] 각 문서 버전이 카드사와 상품코드를 포함한 고유 식별자로 구분된다.
- [ ] 같은 내용의 재실행에서 새 문서 버전 또는 중복 물리 파일이 불필요하게 생성되지 않는다.
- [ ] 신규·변경·동일·실패·사라짐의 합계가 해당 실행에서 발견한 전체 항목과 대사된다.
- [ ] 실패 항목마다 오류 분류, attempt, 마지막 오류와 다음 조치가 기록되어 있다.
- [ ] 허용되지 않은 host, 과대 응답, HTML 응답 및 손상 PDF에 대한 검증 테스트가 통과한다.
- [ ] 최초 최신본 우선 정책과 이후 증분 정책이 서로 다른 실행 모드로 검증된다.

## 4. OCR 처리기

### 4.1 역할과 경계

OCR 처리기는 검증된 PDF를 페이지 단위로 읽어 한글 원문을 가능한 그대로 재현한 Markdown을 만든다. 요약, 상품 추천, 조건 해석 또는 문구 개선은 OCR의 역할이 아니다.

초기 대량 OCR은 수일 이상 지속될 수 있는 durable job으로 취급한다. 프로세스나 컨테이너가 중단되어도 완료한 문서·페이지를 식별하고 이어서 처리할 수 있어야 한다. 이후에는 신규 또는 PDF 내용이 변경된 문서만 처리한다.

LLM 제공자와 모델 운용 규칙은 `05_LLM_AND_DATA_QUALITY_POLICY.md`를 따른다.

### 4.2 입력

- 수집 단계에서 검증 완료된 PDF와 문서 버전 정보
- PDF 해시와 페이지 수
- 페이지 렌더링 정책
- OCR prompt·출력 계약 버전
- 실제 사용할 backend와 모델 설정
- 동일 PDF·정책 조합의 기존 페이지·문서 처리 상태

### 4.3 출력

- 페이지 경계를 식별할 수 있는 문서별 OCR Markdown
- PDF 페이지와 OCR 범위의 대응 정보
- 제목, 본문, 목록, 표, 혜택 조건, 제외조건, 유의사항과 각주 관계를 보존한 전사 결과
- PDF/OCR 해시, 페이지 수, 실제 backend·모델, 실행 정책 버전 및 처리 시각을 포함한 provenance
- 페이지 또는 처리 chunk별 성공·실패·검토 상태
- 품질 검사 결과와 검토가 필요한 위치

렌더 이미지는 재현 또는 감사에 필요한 기간 동안 외부 작업 볼륨에 둘 수 있다. 이미지 보존 기간과 최종 보존 여부는 `결정 필요`이며 Docker 이미지나 Git에는 넣지 않는다.

### 4.4 OCR 원문 계약

- 페이지 순서와 페이지 경계를 보존한다.
- 제목 계층, 문단, 목록 번호, 표의 행·열 머리글과 셀 관계를 가능한 한 보존한다.
- 금액, 비율, 기간, 횟수, 한도, 부등호와 범위 기호를 임의로 정규화하지 않는다.
- 전월실적 조건, 혜택 한도, 실적 제외, 혜택 제외, 유의사항 및 각주를 생략하지 않는다.
- 반복 머리글·바닥글을 제거하려면 결정론적 규칙과 제거 기록이 있어야 한다. 불확실하면 보존한다.
- 읽을 수 없는 부분은 그 사실과 위치를 표시하고 자연스러운 문장으로 추측해 채우지 않는다.
- OCR 결과에는 원문과 구분되지 않는 요약·설명·추천을 넣지 않는다.

### 4.5 상태, 실패와 재처리

- 문서 상태와 페이지 또는 chunk 상태를 함께 관리한다.
- 페이지별 완료 기록에는 입력 PDF 해시와 OCR 정책 버전을 연결한다.
- 일부 페이지만 실패하면 성공한 페이지 산출물을 보존하되, 문서 전체를 검증 완료로 표시하지 않는다.
- timeout, 일시적 backend 장애와 rate limit은 재시도한다. 반복적인 페이지 누락, 지나치게 짧은 출력, 형식 훼손은 품질 실패로 분류한다.
- 중단 후 재시작 시 입력 해시와 정책 버전이 같은 검증 완료 단위는 건너뛴다.
- PDF, prompt 계약 또는 모델이 변경되면 영향 범위를 명시적으로 새 OCR 세대로 처리한다. 기존 결과는 감사·비교를 위해 보존한다.
- 초기 대량 OCR에서는 Codex exec만 사용하며, 자동 OpenRouter 전환으로 완료율을 꾸미지 않는다.

### 4.6 검증 가능한 완료조건

- [ ] 검증 완료 PDF의 모든 페이지가 정확히 한 번 이상 OCR 결과와 대응되거나 명시적 검토 대상으로 분류된다.
- [ ] 성공 문서는 첫 페이지부터 마지막 페이지까지 순서·경계 누락이 없다.
- [ ] OCR 파일의 실제 해시·문자 수와 metadata 값이 일치한다.
- [ ] metadata가 설정 label이 아니라 실제 호출된 backend·모델과 정책 버전을 기록한다.
- [ ] 표, 각주, 실적 조건과 제외조건이 포함된 gold sample이 승인된 품질 기준을 통과한다.
- [ ] 숫자·단위·부정 표현·범위에 대한 별도 검증 결과가 남아 있다.
- [ ] 의도적인 중단과 재시작 시험에서 완료 단위를 중복 호출하지 않고 남은 단위부터 이어진다.
- [ ] 부분 실패 문서가 검색 가능한 완료 문서로 잘못 게시되지 않는다.
- [ ] 동일 입력·정책 재실행 결과가 중복 문서 버전을 만들지 않는다.

## 5. 구조 분석기

### 5.1 별도 구조 분석이 필요한 이유

카드상품안내장은 혜택 이름과 금액만이 아니라 전월실적, 횟수·월 한도, 적용 대상, 실적·혜택 제외조건, 각주가 함께 해석되어야 한다. Markdown heading이나 단순 키워드만으로 자르면 조건의 적용 범위가 끊어질 수 있다.

따라서 임베딩 전에 별도 구조 분석 계층을 두는 것이 적절하다. 다만 구조 분석은 원문을 새 문장으로 재작성하는 과정이 아니라 검색 단위와 원문 관계를 명시하는 파생 과정이어야 한다.

### 5.2 OCR-only 규칙 방식과 LLM 방식 비교

| 관점 | OCR-only 규칙 방식 | LLM 방식 |
|---|---|---|
| 재현성 | 같은 입력·규칙 버전이면 높음 | 모델·provider·prompt에 따라 변동 가능 |
| 비용과 처리량 | 예측 가능하고 저렴함 | 외부 호출 비용·제한과 지연이 존재 |
| 제목·페이지·문자 위치 보존 | 명시적으로 보존하기 쉬움 | 별도 제약이 없으면 재작성·누락 가능 |
| 다양한 문서 레이아웃 | 카드사별 규칙이 늘어날 수 있음 | 의미 기반 분류와 관계 추론에 유리 |
| 표·각주·조건 적용 범위 | 결정론적 단서가 명확할 때 강함 | 복잡한 문맥 연결에 유리하나 환각 위험 |
| 실패 탐지 | 규칙 불일치와 누락을 계수하기 쉬움 | 그럴듯한 잘못된 결과를 만들 수 있음 |
| 모델 교체 영향 | 없음 | 대규모 회귀 검증과 재처리가 필요 |

규칙만 사용하면 예외적인 레이아웃과 멀리 떨어진 조건 관계를 충분히 포착하기 어렵다. LLM만 사용하면 원문 재작성, 숫자 변경, 제외조건 누락과 재현성 저하를 통제하기 어렵다.

### 5.3 권장안: 원문 불변의 계층형 구조 분석

다음 결합 방식을 권장한다.

1. **원문 불변 계층**: 원본 PDF와 검증 완료 OCR을 변경하지 않는다.
2. **결정론적 후보 계층**: 페이지, heading, 문단, 목록, 표, 각주, 문자 또는 줄 범위를 이용해 layout block과 section 후보를 만든다.
3. **도메인 schema 계층**: 상품·연회비, 주요 혜택, 이용조건, 전월실적, 실적 제외, 혜택 제외, 필수 안내, 유의사항 등의 분류 후보를 부여한다.
4. **schema-guided LLM 보강 계층**: 규칙으로 확정하기 어려운 분류, 조건의 적용 범위, 표와 각주의 연결을 제한된 schema 안에서 보강하거나 검증한다.
5. **대사·검증 계층**: 모든 분류와 관계가 OCR의 실제 범위를 가리키는지, 숫자나 부정 조건을 새로 만들거나 잃지 않았는지 확인한다.

LLM 출력은 원문 대체물이 아니다. LLM이 제시한 정규화 문구는 파생 필드로만 저장하며, 검색 근거와 MCP 인용에는 연결된 OCR 원문을 사용한다. LLM이 원문에서 찾을 수 없는 값을 만들거나 근거 범위를 가리키지 못하면 해당 값은 거부한다.

### 5.4 입력

- 검증 완료 OCR Markdown과 페이지 대응 정보
- 문서 버전 및 카드사·상품 metadata
- 결정론적 layout parser와 도메인 taxonomy 버전
- 구조 출력 schema와 검증 규칙
- 선택적인 LLM prompt·모델 정책

### 5.5 출력

- 페이지와 OCR 범위를 보존한 layout block
- section 후보와 canonical 분류
- 혜택, 조건, 한도, 실적·혜택 제외, 각주 사이의 근거 연결
- 규칙 추출과 LLM 보강을 구분한 extraction method
- 원문 범위, 신뢰 상태, 검증 오류와 검토 필요 사유
- 구조 schema·규칙·LLM 정책 버전을 포함한 generation manifest

구조 결과에 표시용 정규화 텍스트가 있더라도 원문 인용과 분리한다. 각 사실 단위는 하나 이상의 OCR 근거 범위 또는 명시적인 `근거 없음` 상태를 가져야 한다.

### 5.6 상태, 실패와 재처리

- 결정론적 후보 생성과 LLM 보강 상태를 분리한다. LLM 장애가 결정론적 결과까지 잃게 해서는 안 된다.
- schema 위반, 존재하지 않는 원문 범위 참조, 숫자 불일치, 부모 없는 각주, 서로 모순되는 관계는 자동 게시하지 않는다.
- LLM timeout이나 출력 오류는 문서 단위로 재시도하고, 승인된 정책에 따라 OpenRouter로 전환할 수 있다.
- OCR 내용 해시가 같고 구조 규칙·schema·LLM 정책이 같으면 검증 완료 구조 결과를 재사용한다.
- taxonomy나 schema 변경은 구조 분석 이후 단계만 새 generation으로 재처리한다.
- 규칙 결과와 LLM 결과가 충돌하면 원문을 우선하고 충돌을 기록한다. 조용히 한쪽을 채택하지 않는다.

### 5.7 검증 가능한 완료조건

- [ ] 모든 구조 block과 사실 단위가 존재하는 문서 버전과 OCR 범위를 참조한다.
- [ ] 페이지·범위 참조가 OCR 경계를 벗어나거나 서로 다른 문서로 연결되지 않는다.
- [ ] LLM이 만든 모든 분류·관계·정규화 값이 원문 근거와 대사되거나 검토 대상으로 분류된다.
- [ ] 연회비, 혜택, 전월실적, 실적 제외, 혜택 제외, 필수 안내 및 유의사항의 누락 검사가 수행된다.
- [ ] 표 머리글과 데이터 셀, 각주와 대상 문구의 관계가 gold sample에서 검증된다.
- [ ] 규칙-only 결과와 LLM 보강 결과를 별도로 재현·비교할 수 있다.
- [ ] LLM 사용 불가 시 결정론적 후보 계층은 유지되고 실패 상태가 정확히 노출된다.
- [ ] 구조 schema 또는 모델 변경 시 이전 generation과 품질 회귀 비교가 가능하다.
- [ ] 구조 결과를 제거해도 원본 PDF와 OCR 원문은 영향을 받지 않는다.

## 6. 임베딩 및 색인

### 6.1 역할과 경계

임베딩·색인 구성요소는 검증된 OCR과 구조 결과를 검색 가능한 단위로 만들고, 온라인 MCP가 읽을 immutable 검색 세대를 게시한다. 문서 내용을 요약해 원문을 대체하거나 검증되지 않은 문서를 게시하는 역할은 아니다.

초기에는 전체 corpus를 새 generation으로 만들고, 이후에는 신규·변경·삭제 상태를 반영한 증분 build를 지원한다. 증분 처리도 최종적으로는 완결된 독립 generation을 만들어야 하며 운영 중인 DB 테이블을 drop/recreate해서는 안 된다.

### 6.2 입력

- 게시 대상으로 승인된 문서 버전 목록
- OCR 원문, 페이지·범위와 구조 분석 결과
- 문서·OCR 내용 해시와 schema generation
- chunking 정책과 검색 metadata 정책
- OpenRouter 임베딩 전용 모델 설정
- 이전 게시 generation과 변경 집합
- 검색 품질 gold query 및 기대 근거 집합

### 6.3 검색 단위 구성

- 혜택 본문과 그 적용 조건·한도·제외조건을 가능한 한 함께 검색할 수 있게 한다.
- 표 머리글과 셀, 각주와 대상 본문이 분리될 때에는 관계 metadata 또는 적절한 중첩을 유지한다.
- 너무 긴 단위는 의미 경계를 따라 나누고, 인접 맥락과 원문 위치를 보존한다.
- 안정적인 evidence 식별자는 카드사, 문서 버전과 원문 범위에 기반하며 검색 순위에 의존하지 않는다.
- 모든 단위에 카드사, 상품코드, 상품명, 문서 버전, 기준일, section, 페이지·원문 범위와 내용 해시를 연결한다.
- 기본 검색은 최신본만 대상으로 하고 과거 version·기준일 조회는 명시적 요청으로 분리한다. 이를 단일 색인의 filter로 구현할지 별도 색인으로 구현할지는 benchmark 후 결정한다.

### 6.4 출력

- 원문 조회를 위한 lexical/FTS 계층
- 승인된 임베딩 모델로 만든 vector 계층
- 공통 evidence 식별자로 연결되는 metadata 계층
- 모델, 차원, chunk 정책, 입력 generation과 row/hash coverage를 기록한 index manifest
- 품질 평가, 무결성 검사와 성능 측정 결과
- 온라인 서비스가 읽을 수 있는 immutable 검색 generation
- 현재 generation을 가리키는 원자적 게시 정보와 이전 generation rollback 정보

검색 구현 방식과 저장 기술은 `결정 필요`다. 레거시처럼 모든 4,096차원 BLOB을 요청마다 Python에서 전수 순회하는 방식은 온라인 기본 경로로 채택하지 않는다. ANN 또는 동등한 bounded 검색 방식의 정확도와 운영 복잡도를 비교해야 한다.

### 6.5 상태, 실패와 재처리

- chunk 생성, 임베딩 요청, 색인 build, 검증, 게시 상태를 분리한다.
- 임베딩은 내용 해시, 모델, 차원, 입력 형식이 모두 같은 경우에만 재사용한다.
- 응답 개수, 차원, 유한값 여부와 입력 순서 대응을 검증한 뒤 저장한다.
- 일부 임베딩 실패가 있으면 generation 전체를 게시하지 않거나, 사전에 승인된 degraded 정책을 명확히 적용한다. 허용 coverage 기준은 `결정 필요`다.
- 모델 또는 차원이 바뀌면 기존 벡터와 혼합하지 않고 새 전체 generation을 만든다.
- 삭제 또는 더 이상 최신이 아닌 문서는 새 generation에서 조회 범위에 맞게 제외하되 이력 보존 정책을 따른다.
- 새 generation은 별도 위치에서 완성·검증한 뒤 원자적으로 게시한다. 실패하면 현재 서비스 generation을 유지한다.
- stale embedding은 row 수를 채우는 데 사용하지 않으며 현재 content hash와 join한 coverage로 완료를 판단한다.

### 6.6 검증 가능한 완료조건

- [ ] 게시 대상 문서·구조 단위와 lexical/vector row의 수 및 content hash coverage가 대사된다.
- [ ] 모든 vector의 모델, 차원, 값 유효성과 원문 단위 연결이 검증된다.
- [ ] 이전 모델·이전 내용의 stale vector가 현재 검색 후보에 섞이지 않는다.
- [ ] issuer, 문서 버전, 기준일 및 section filter가 후보 검색 전에 적용되거나 동일한 정확도를 보장한다.
- [ ] lexical과 vector 결과가 공통 evidence ID로 결합되고 카드사 간 상품코드 충돌이 없다.
- [ ] gold query에서 혜택 조건, 전월실적, 실적·혜택 제외와 각주 근거의 검색 품질이 승인 기준을 통과한다.
- [ ] query embedding은 document embedding과 호환되는 동일 모델·입력 정책을 사용한다.
- [ ] 새 generation 검증 실패 시 현재 generation이 중단 없이 유지되는 것이 확인된다.
- [ ] 게시와 rollback이 부분 세대 노출 없이 동작하는 통합 시험이 통과한다.
- [ ] 목표 corpus 규모와 예상 동시성에서 latency·메모리·I/O 기준을 충족한다. 목표치는 `결정 필요`다.

## 7. MCP 서비스

### 7.1 역할과 경계

MCP 서비스는 외부 LLM이 카드상품 정보를 검색하고 근거 원문을 상세 조회할 수 있게 하는 상시 실행 읽기 전용 서비스다. 검증 완료 후 게시된 한 개의 검색 generation을 일관되게 읽는다.

다음 범위를 제공한다.

- 카드사·상품명·질문에 따른 카드상품 근거 검색
- 카드사와 상품코드로 특정 상품 및 문서 버전 조회
- 주요 혜택과 이용조건 조회
- 전월실적, 실적 제외와 혜택 제외조건 조회
- 특정 상품의 버전 이력 및 기준일 조회
- 검색 generation, 데이터 기준 시점과 카드사 범위 확인
- 검색 결과의 전체 원문 근거를 안정적인 식별자로 후속 조회
- 페이지 단위 OCR·원문 근거 조회
- 사용자가 명시적으로 요청한 정확한 문서 버전의 보존 원본 PDF 파일 제공

구체적인 tool/resource 이름, 인자와 응답 schema는 구현 단계에서 결정한다. MCP 서비스는 카드사 사이트 PDF 수집, OCR, 임베딩 build, DB 재구축, 임의 URL 다운로드, Codex privileged 실행 또는 이메일 발송을 동기식 요청으로 수행하지 않는다. 원본 PDF 제공은 이미 보존되어 게시 승인된 전체 파일의 읽기 전용 streaming이며 신규 수집 기능이 아니다. 페이지 조회는 OCR text와 선택적 렌더 PNG를 사용하고 분할 PDF는 생성하지 않는다.

### 7.2 입력

- 자연어 검색 질의
- 선택적인 카드사, 상품코드, section, 기준일·문서 버전과 결과 범위
- 안정적인 evidence 또는 문서 식별자를 이용한 상세조회 요청
- 선택적인 페이지 범위, 페이지 PNG 포함 여부와 원본 PDF 전체 파일 제공을 명시하는 요청
- vector 장애 시 lexical-only 결과를 허용하는 명시적 `allow_degraded` flag
- 호출자 권한과 요청 제한 정보

입력 enum, 문자열 길이, 결과 수와 timeout에 경계를 둔다. 외부 입력을 파일 경로나 SQL 조각, 다운로드 URL 또는 subprocess 인자로 직접 사용하지 않는다.

### 7.3 출력

- 카드사, 상품코드, 상품명과 문서 버전·기준일
- 관련 section과 질문에 충분한 원문 근거
- 페이지·원문 범위, 출처 URL 또는 보존 경로, 내용 해시
- 안정적인 evidence ID와 검색 generation
- 원본 PDF 요청 시 exact document version, SHA-256, MIME type, 파일 크기와 인증된 streaming file 응답
- 페이지 요청 시 OCR text와 요청한 경우에만 렌더 PNG resource; 분할 PDF는 제공하지 않음
- retrieval 방식과 결과 해석에 필요한 점수 또는 품질 상태
- 최신·과거 버전 충돌, 정보 부족, 부분 검색 또는 degraded 상태의 명시적 표시

상위 검색 결과 몇 개만 잘라 반환해서 조건과 제외 문구를 잃지 않도록 한다. 긴 원문은 안정적인 resource 또는 pagination 방식으로 이어서 조회할 수 있어야 하며, 첫 응답에는 연결 정보를 포함한다.

### 7.4 조회 및 근거 정책

- 검색 후보 선정 전에 가능한 범위에서 카드사, 버전, 기준일과 section filter를 적용한다.
- lexical과 vector를 결합할 경우 서로 다른 ID 공간을 순위 점수만으로 합치지 않고 공통 evidence 단위로 fusion한다.
- query embedding을 여러 검색 경로에서 중복 호출하지 않는다.
- 응답 문구와 정규화 사실은 항상 반환된 원문 근거로 확인 가능해야 한다.
- 서로 다른 문서 버전이 충돌하면 하나로 합쳐 확정하지 않고 버전별로 구분한다.
- 근거가 없거나 검색 범위를 벗어난 질문은 추측하지 않고 부족함을 알린다.
- 최신 조회에는 현재 generation의 기준 시점을 함께 제공한다.
- 원본 PDF는 사용자가 명시적으로 요청하고 권한을 통과한 경우에만 exact version과 content hash로 해석한다. host path나 임의 URL을 응답하지 않는다.
- 페이지 조회는 PDF page와 OCR source span을 함께 식별해 재검증할 수 있어야 하며, PNG는 명시적으로 요청된 경우에만 제공한다.
- 일반 검색과 페이지 OCR text에는 `search`, 원본 PDF 전체 파일과 페이지 PNG에는 `source_pdf` scope를 요구한다.

### 7.5 상태와 장애 처리

- liveness와 readiness를 구분한다. 프로세스가 살아 있어도 활성 generation 무결성, schema, 모델·차원 및 필수 index가 맞지 않으면 ready가 아니다.
- 요청 하나가 읽는 동안 generation이 바뀌어도 서로 다른 세대의 metadata와 vector를 섞지 않는다.
- 새 generation 게시 실패는 현재 읽기 서비스에 영향을 주지 않는다.
- query embedding 또는 vector 검색 장애 시 `allow_degraded=true`인 요청만 lexical-only 결과를 반환한다. 응답에 `degraded` 상태와 실패한 검색 branch를 명시하며, flag가 없거나 false이면 요청을 실패시킨다.
- 최초 OAuth 승인 후 access token은 client가 자동 갱신하고 refresh token은 매 사용 시 회전한다. 90일 비활성 전에는 정상적인 지속 사용에서 수동 token 재입력을 요구하지 않는다. refresh 폐기·분실·보안사고·client 미지원은 재인증 사유다.
- timeout, 과도한 결과 요청과 동시성 초과에 대해 bounded 실패를 반환한다.
- 감사 로그에는 원문·질의·개인정보를 무제한 저장하지 않고 요청 ID, generation, 처리 상태와 제한된 운영 metadata를 남긴다.

### 7.6 검증 가능한 완료조건

- [ ] 서비스가 수집·OCR·색인 작업용 쓰기 권한 없이 검색 snapshot을 읽을 수 있다.
- [ ] 검색, 상품 상세, 혜택 조건, 전월실적·제외조건, 버전 충돌 시나리오가 검증된다.
- [ ] 모든 근거 응답에 issuer-scoped 식별, 문서 버전, generation과 원문 위치가 포함된다.
- [ ] evidence ID로 후속 조회한 원문이 최초 검색 결과의 인용과 동일한 content hash를 가진다.
- [ ] 같은 상품코드를 가진 서로 다른 카드사의 결과가 섞이거나 중복 제거되지 않는다.
- [ ] 근거 부족 질문과 상충하는 버전에 대해 추측 대신 명시적 불확실성을 반환한다.
- [ ] generation 교체 중 실행한 요청이 부분 세대 또는 테이블 부재를 관찰하지 않는다.
- [ ] 활성 generation 손상, schema 불일치 또는 vector dimension 불일치 시 readiness가 실패한다.
- [ ] query 입력·결과 수·timeout·동시성 제한과 취소가 통합 시험에서 확인된다.
- [ ] 원본 PDF 응답이 요청한 version·SHA-256과 일치하고 권한·크기·streaming·감사 정책을 통과한다.
- [ ] 페이지 조회 결과가 동일 문서 version의 PDF page와 OCR source span으로 역추적된다.
- [ ] 페이지 PNG는 명시적 요청에서만 제공되고 분할 PDF가 생성되지 않는다.
- [ ] access token 만료 전 자동 refresh, refresh token rotation, 90일 비활성 만료와 revoke·재인증 흐름이 통합 시험에서 확인된다.
- [ ] vector 장애 시 `allow_degraded` 유무에 따른 lexical-only 또는 실패 동작과 상태 표시가 검증된다.
- [ ] 초기 동시 요청 5개에서 품질 손실 없이 bounded 응답한다. 목표 latency, 처리량과 가용성 수치는 BULK pilot 후 결정한다.

## 8. 구성요소 인계 기준

| 발신 단계 | 수신 단계 | 인계 필수조건 |
|---|---|---|
| PDF 수집 | OCR | PDF 존재, 해시 일치, 페이지 열기 가능, 문서 버전과 출처 기록 완료 |
| OCR | 구조 분석 | 모든 페이지 상태 대사, OCR 해시·provenance 일치, 품질 gate 통과 |
| 구조 분석 | 임베딩·색인 | 원문 범위 참조 무결성, schema 검증, 미해결 오류 격리 |
| 임베딩·색인 | MCP | current hash coverage, 검색 품질·성능·무결성 gate, immutable generation 게시 완료 |
| MCP | 외부 LLM | 원문 근거, 버전·generation, 불확실성과 충돌 상태를 함께 제공 |

선행 단계가 `검증 완료`가 아니면 후행 단계의 정상 corpus에 포함하지 않는다. 예외적으로 검토용 환경에서 불완전 데이터를 사용할 경우 운영 generation과 물리·논리적으로 분리하고 결과에 그 상태를 표시한다.
