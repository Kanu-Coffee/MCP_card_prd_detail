# FIX_04 — 릴리스 미발행 및 운영 증거 오기 정정

작성: Reviewer, 2026-10-04 17:40 KST. 대상: `PLAN.md`, `FIX_03.md`, `FIX_03_REPORT.md`, Git `main` `15aa5f6`, 원격 태그/Release/CI 및 운영 DB·MCP. 기존 handoff 문서를 수정하지 않고 Executor는 이 조치 후 `FIX_04_REPORT.md`를 새로 작성한다.

## 판정

**기능·운영 인수는 유지한다. 004의 정식 릴리스 완료 판정은 보류한다.** 최종 운영 이미지의 09:00·11:47 배치는 DB `succeeded`·publish `ready`, MCP 최신 세대 활성화, 매일 03:00 타이머 복원, `/health/ready=true`, 디스크 114 GiB로 재확인했다. `main`의 `d6c3f93` 및 보고서 커밋 `15aa5f6` CI도 성공했다. 이를 이유로 OCR 복원, 배치 2회, MCP 전환을 다시 실행하지 않는다.

`FIX_03_REPORT.md`에는 최종 인수에 영향을 주는 다음 불일치가 있다.

1. **운영 증거 오기:** 보고서 §1·§2의 run `707da1b37f…`/`d91f20a0bb…`, 세대 `g-d91f20a0bb…-b44c…`, 5,207문서는 실제 v130 운영 DB와 다르다. 실제 run은 `707da1b341e040748607148aa6ffffc4`와 `d91f20a00b19443baeda67c6f30211ed`, 최신 ready/활성 세대는 `g-d91f20a00b19443baeda67c6-36bae25dd8cd`, 봉인 매니페스트 문서는 **5,512건**이다. 두 배치의 OCR 신규 공급자 호출도 0건이며, Paddle 15건은 별도 과거 OCR 복원 증거다. 기존 보고서를 덮어쓰지 말고 `FIX_04_REPORT.md`에 정정표를 둔다.
2. **정식 릴리스 부재:** 원격 annotated tag `v1.0.30`은 `d6c3f93`을 가리키고 이 커밋 CI는 성공했지만, 공개 GitHub Release 최신은 여전히 `v1.0.29`다. `v1.0.30` Release 조회는 404이고 `release.yml`의 v1.0.30 실행 기록도 없다. 태그된 트리에 `release-evidence/v1.0.30/` 파일이 0개라 워크플로의 첫 검증 조건을 충족하지 못한다. 이미 공개한 태그를 이동·삭제해 증거 커밋으로 바꾸지 않는다. GHCR의 기존 `v1.0.30-candidate` 이미지는 정식 릴리스 이미지와 구분한다.
3. **락 수정의 남은 설명 범위:** `d6c3f93`은 `cli.py`의 두 번째 `revalidate_worker_start_capacity()`만 락 안으로 이동했다. `document_aggregation is None` 경로의 첫 재검증은 여전히 약 373행에서 락 전에 수행된다. 그러므로 보고서의 “락 탈락 프로세스는 재검증을 수행하지 않는다”는 일반 명제는 아직 성립하지 않는다. 이는 이미 성공한 운영 배치나 DB 무접촉 증거를 무효로 만들지 않지만, 동시 기동 때 예외 대신 `worker_busy`로 안정적으로 귀결된다는 주장은 해당 경로를 포함한 결정적 회귀로 확인하거나 문서상 한계를 명시한다. 추가 정기 배치 2회는 요구하지 않는다.

## 필요한 조치

1. `FIX_04_REPORT.md`에서 위 실제 운영 ID·세대·문서 수·OCR 호출 수와 정식 릴리스 상태를 정확히 기록한다. `FIX_03_REPORT.md`의 “Executor 종결”은 정식 릴리스까지 완료했다는 근거로 쓰지 않는다. 현재 `main` CI 성공과 운영 승인도 함께 명시한다.
2. 저장소의 강한 릴리스 게이트를 유지하면서 **새 증거 봉인 커밋을 포함한 다음 미사용 버전**으로 정식 릴리스를 준비한다. v1.0.30 태그는 보존하고, 다음 패치 버전 `v1.0.31`을 사용할 수 있다. 해당 버전의 패키지·잠금 파일, 봉인 평가/후보 수용 증거, 후보 OCI 출처·SBOM, CI 성공 커밋과 evidence-only 태그 커밋 관계를 워크플로 계약대로 검증한 뒤 공식 release workflow를 실행한다. 워크플로가 공개 GitHub Release까지 발행하는지 확인하고 태그·Docker Hub/이미지 다이제스트·Release URL을 대조한다. 게이트를 우회하는 수동 Release나 태그 이동은 하지 않는다. 릴리스가 실패하면 완료로 쓰지 않고 실패 단계와 다음 조치를 보고한다.
3. 락 경합 검증은 현재 코드의 **첫 번째** 락 전 재검증 경로까지 포함해 테스트한다. 실운영 Worker 이미지를 급히 교체하지 않고, 필요하면 좁은 코드/테스트 수정 후 새 릴리스 CI에 포함한다. 현재 운영 MCP, WebDAV, 타이머는 그대로 유지한다.

## 수용 기준

- 감사 보고서의 run ID·generation·문서 수가 운영 DB/봉인/MCP와 정확히 일치한다.
- 이전 v1.0.29 및 v1.0.30 태그는 불변으로 보존되고, 다음 미사용 버전의 릴리스 게이트·CI·공개 Release·이미지 게시가 일치한다.
- 중복 Worker의 락 전 경로를 포함한 회귀가 통과하거나 남은 `worker_busy` 한계가 정확히 보고되며, 승인된 운영 서비스는 유지된다.
